Business Intelligence and Dashboards module

Public sector Power BI dashboard

Role
Data analyst and dashboard designer
Problem
My assigned client was a Programme Targeting Officer at an international development agency who needed to choose three countries for a climate adaptation programme, using large sets of country data that were hard to compare.
Solution
I cleaned and modelled the data in Power Query, then designed an interactive dashboard with KPI cards, filters and comparison visuals so the officer could rank countries against the programme’s criteria.
Outcome
I presented the finished dashboard in my week 6 seminar and used it to justify a shortlist of three countries.
  • Power BI
  • Power Query
  • Data modelling
  • Data storytelling
Personal project, ongoing

Custom trading indicator

Role
Independent researcher and developer
Problem
After several years of trading gold, my results were inconsistent because I kept changing strategy and took entries on emotion rather than clear rules.
Solution
I turned my strategy into written rules based on higher-timeframe liquidity sweeps and lower-timeframe entries, then back-tested variations across gold and major currency pairs to see which actually had an edge.
Outcome
Back-testing ruled out most variations and left one evening setup worth developing. I am now building it into an automated Python bot tested on a demo account before any real money is used.
  • Rules-based logic
  • Back-testing
  • Python
  • Risk management

Design concept

Development rationale behind the Problem-Solving Page

Every structural choice on the Aurum page links back to one of the four goals in the case study, which are engagement, efficiency, customer experience and promotion.

1. Story-led page order

The page follows the journey a real guest takes. They discover the restaurant, browse the menu, notice a promotion, join the loyalty scheme and finally book. Putting the booking form last means users arrive at it already persuaded, which follows the AIDA model of attention, interest, desire and action.

2. Responsive across screen sizes

Most restaurant searches happen on a phone, so the page had to work just as well on a small screen as on a laptop. I built the layout with CSS Grid, then used media queries at 960px and 760px to collapse it into a single column and swap the navigation for a menu button. I tested each section at phone width as I built it. The menu uses tabs so diners are not faced with one long scrolling list. On reflection, writing the CSS mobile-first would have meant less code to override on small screens, and I would do that on the next version.

3. Efficiency without a database

The brief did not require a back end, so the form uses JavaScript to validate input and build a structured email. Staff receive every booking in the same format, which reduces phone calls and errors without the cost of a booking platform.

4. Accessibility and trust

I used semantic HTML, labelled form fields, keyboard-friendly tabs, visible focus states, strong colour contrast and a reduced-motion setting, following WCAG 2.2 guidance. A clear privacy notice and cookie banner show the restaurant takes UK GDPR seriously, which builds trust before users share personal data.

5. Visual identity

A dark background with champagne gold and a serif heading font communicates a luxury fine-dining brand. I reused my portfolio’s colour tokens so both feel like one professional product.

6. Testing and validation

I validated every page with the W3C HTML and CSS validators, tested on desktop, tablet and mobile screen sizes in Chrome and on my phone, and checked every internal link and image before deploying through GitHub Pages.
